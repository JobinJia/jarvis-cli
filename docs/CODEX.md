# Codex CLI integration

`jarvis-cc` was built around [Claude Code](https://claude.com/claude-code)
but Codex CLI's hook system is close enough that adding support amounted
to one extra branch in the hook translator. After install, Codex
permission prompts, end-of-turn waits, and tool-use lifecycle events all
flow through the same Jarvis pipeline.

## Event mapping

| Codex event | Codex transport | Daemon event | What Jarvis says |
|---|---|---|---|
| `PermissionRequest` | lifecycle hook | `permission_prompt` | "Sir, he intends `<command>` — your verdict?" |
| `agent-turn-complete` | `notify` array | `idle_prompt` | "Sir, Claude awaits your guidance." |
| `UserPromptSubmit` | lifecycle hook | (cancel) | — kills in-flight audio for that session |
| `PostToolUse` | lifecycle hook | (cancel) | — same |
| `PreToolUse` | lifecycle hook | (no-op unless `AskUserQuestion`) | Codex has no AskUserQuestion tool, so PreToolUse fires but is filtered by the daemon's `events =` allowlist |
| `SessionStart` / `Stop` | lifecycle hook | dropped | Intentional silence — not announcement-worthy. |

Cancel-on-user-action behavior works for Codex without any extra setup:
Codex shares Claude Code's `UserPromptSubmit` and `PostToolUse` event names
and payload shape, so the existing cancel pipeline routes Codex's
"user responded" signals correctly.

## Auto-install (recommended)

If `~/.codex/config.toml` (or even `~/.codex/`) exists on the machine
when you run `jarvis-cc install`, the installer auto-patches it:

```bash
uv run jarvis-cc install
# ...
#   patched ~/.claude/settings.json (hook → /abs/jarvis-cc-hook)
#   patched ~/.codex/config.toml (Codex CLI detected)
# ...
```

The patch is wrapped in marker comments:

```toml
# === jarvis-cc:start ===
# Auto-generated by `jarvis-cc install`. Anything between these
# markers is replaced on the next install; remove via `jarvis-cc uninstall`.

notify = ["/abs/jarvis-cc-hook"]

[[hooks.PreToolUse]]
matcher = ".*"
[[hooks.PreToolUse.hooks]]
type = "command"
command = "/abs/jarvis-cc-hook"
timeout = 5

[[hooks.PermissionRequest]]
matcher = ".*"
[[hooks.PermissionRequest.hooks]]
type = "command"
command = "/abs/jarvis-cc-hook"
timeout = 5

[[hooks.UserPromptSubmit]]
[[hooks.UserPromptSubmit.hooks]]
type = "command"
command = "/abs/jarvis-cc-hook"
timeout = 5

[[hooks.PostToolUse]]
[[hooks.PostToolUse.hooks]]
type = "command"
command = "/abs/jarvis-cc-hook"
timeout = 5
# === jarvis-cc:end ===
```

The installer inserts this block *between* your existing top-level keys
(`model`, `developer_instructions`, etc.) and your first `[section]`
header, so TOML stays valid. Re-running `jarvis-cc install` replaces
the block in place; `jarvis-cc uninstall` strips it.

Anything outside the markers is left untouched.

## Manual install

If you prefer to wire it up by hand (or you already have a hook setup
you don't want overwritten), copy the block above into your
`~/.codex/config.toml`, replacing `/abs/jarvis-cc-hook` with the
absolute path on your machine:

```bash
which jarvis-cc-hook
# /Users/me/code/jarvis-cc/.venv/bin/jarvis-cc-hook
```

Restart Codex (or wait for its config-reload — easiest is `codex`-quit
and relaunch) and the next permission prompt should speak.

## Verify

After install:

```bash
# 1. confirm Codex sees the patch
codex --help >/dev/null   # any Codex command exercises config load
grep -c "jarvis-cc-hook" ~/.codex/config.toml   # → 4 (one per hook event)

# 2. fire a no-op Codex run that asks for permission
codex exec "run: ls /"
# When the approval prompt appears, you should hear:
#   "Sir, he intends to run `ls /` — your verdict?"
```

If Jarvis stays silent, check:

```bash
tail ~/.jarvis-cc/daemon.log
# look for: jarvis_cc.daemon.listener — incoming permission_prompt
```

## Caveats

- **PreToolUse fires frequently.** Codex sends a hook for every tool
  call, not just permission-needing ones. The daemon's
  `cfg.behavior.events` allowlist filters anything that isn't in
  `[permission_prompt, idle_prompt, elicitation_dialog, ask_user_question]`,
  so most PreToolUse events get dropped silently — which is what you
  want. If you ever change that allowlist, expect a lot of Jarvis chatter.
- **Codex's `notify` only fires `agent-turn-complete` today.** Other
  notify types may be added later; the translator ignores them
  (returns the raw payload, daemon filters it out) until we add a
  branch.
- **No streaming hook responses.** We use Codex's command-hooks as
  fire-and-forget — `jarvis-cc-hook` returns immediately, the daemon
  speaks asynchronously. We don't `allow` / `deny` permission
  requests; that stays a user decision in Codex's UI.
- **One daemon, both clients.** Run jarvis-cc once; both Claude Code
  and Codex sessions share the same daemon, dedup window, and audio
  cancellation behavior.

## Uninstall

```bash
uv run jarvis-cc uninstall
# ...
#   cleaned ~/.claude/settings.json
#   cleaned ~/.codex/config.toml
# ...
```

This removes our managed block from `~/.codex/config.toml` (matched
by the sentinel comments) and leaves the rest of the file untouched.
